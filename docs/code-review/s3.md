# s3（L2）评审明细

> 覆盖 `src/s3/`：service / router / auth（sigv4 / credential_store）/ handlers
> （objects / multipart / buckets / list_objects / admin_credentials / common.h）/
> xml / errors。跨模块问题（认证 fail-open、`percent_decode` 的 `+`）见
> [README.md](README.md) §1.2 / §1.3。

**模块级评价**：结构清晰、边界意识强（`.sys` 多处拦截、copy-source 单独授权、
write-through 顺序、恒定时间比较、XML 不展开实体都做对了）。系统性问题有三类：
**验签的"完整性校验"依赖下游读到 EOF、而 cloudproxy 后端不会**（payload 校验对该后端
形同虚设）；**若干客户端可控输入未设上限/未严格校验**（max-keys、amz-date 年份、空
摘要）；以及**条件写/条件读非原子且判定时机偏晚**。

## 高

### [高 · ✅已复核] x-amz-content-sha256 校验与 aws-chunked 末块签名在 cloudproxy 后端从不执行
`src/s3/auth/sigv4.cc:135-147`（`Sha256VerifyingReader::read` 只在 `n==0` 分支比对）、`:194-223`（`ChunkedSigV4BodyReader` 的 chunk 签名/长度对账只在下一次 read 的归零处触发）；消费者 `src/storage/cloudproxy/cloudproxy_backend.cc:557` `while (sent < len)`（`len = body.length()`）。

**机制**：两个校验装饰器都把判定挂在 EOF 那一次 `read()` 返回 0 上。cloudproxy 生产者读满自报长度即退出，**永不再调 read()** → hex 摘要完全不验；signed chunked 模式下末块与 0 号尾块签名都不验，签名链在倒数第二块断掉，长度对账也不执行。其它 5 个后端是 `for(;;){n=read(); if(!n)break;}` 读到 EOF——契约没写下来，只是碰巧成立。**触发**：路由到 cloudproxy 的桶 `PUT` 带任意错误 `x-amz-content-sha256` → 200 且不报错。对能改写在途请求的中间人是签名保护的实际缺口。**建议**：校验不绑 EOF（读满 `length()` 即比对 + 析构断言）；`cloudproxy_backend.cc:557` 循环改为读到 0 为止（零成本多读一次）；把"body 须读到 EOF / 抛异常则不得提交对象"写进 storage-backend 契约。

### [高 · ✅已复核] ListObjects 的 max-keys 无上限，单请求即可把整桶列表构造进内存
`src/s3/handlers/list_objects.cc:12-18`（`stoi` 后只拒 `<0`）、`:24` 起 XmlWriter 全量拼进 `resp.small_body`。无 S3 的 1000 钳制。对百万级对象的桶发 `?list-type=2&max-keys=2147483647` → 数百 MB~GB XML → 单进程 OOM 打掉所有租户；localfs 还同步遍历整棵目录树。**建议**：`max_keys = min(max_keys, 1000)`（S3 语义即静默钳制）；或响应流式化。

### [高 · confirmed] 认证 fail-open（凭证表运行期变空）
详见 [README.md](README.md) §1.2。`sigv4.cc:389` + `credential_store.cc` 的 `apply_file_credentials`/`sync_now` 可把 `creds_` 清空导致匿名开放。

## 中

### [中 · confirmed] parse_amz_date 对四位年份不设限 → chrono 有符号溢出 UB，并绕过"未来时间戳"防护
`sigv4.cc:418` → `core/util/time.cc:73-83`。`sscanf("%4d…")` 接受 9999 年，`timegm`≈2.53e11 秒，`from_time_t` ×1e9 → 2.5e20 超 int64 → 溢出 UB。发生在凭证查表/签名比对**之前**，未认证可达。回绕还使 `sigv4.cc:423`（presigned 未来 15min 防护）与 `:437`（时钟偏移）形同虚设——4 位年份区间覆盖约 13 个 2^64 ns 周期，必存在若干年份回绕进当前 ±15min 窗口。**建议**：`timegm` 后钳制/拒绝 year>2999，并校验 sscanf 完整消费。

### [中 · confirmed] `?versionId` 未拒绝，`DELETE ?versionId=` 静默删当前对象
`service.cc:39-46` `kUnsupportedSubresources` 含 `"versions"` 但不含 `"versionId"`；路由兜底吃下它。`handlers/common.h:66` 对 copy-source 的 versionId 是拒绝的，直接对象路径漏了。按版本清理的工具会误删活数据。**建议**：把 `"versionId"` 加进拒绝表。

### [中 · confirmed] 声明空 payload 摘要时跳过 body 校验，body 脱离签名保护
`sigv4.cc:496`：为给真·空 body 省一次哈希，把 `x-amz-content-sha256: e3b0c442…` 排除校验，但不检查 body 是否真空 → 空摘要 + 非空 body 被原样落盘。捕获一条合法空 body PUT，追加 Content-Length + 内容即注入。**建议**：空摘要照样包 `Sha256VerifyingReader`，或断言 body 长度为 0。

### [中 · plausible] 不强制 host ∈ SignedHeaders，vhost 下 presigned 可跨桶重指向
`sigv4.cc:388-500`。AWS 规定 host 必签，此处只小写化 signed_headers 不检查是否含 host（presigned 甚至允许 SignedHeaders 缺失）。vhost 下 bucket 来自 Host 头；签名未绑 host 时，同一 presigned 签名在任意 `*.base_domain` 上都成立 → 改 Host 即跨桶。**建议**：强制 signed_headers 含 host（presigned 亦然）。

### [中 · confirmed] 条件请求在 get_object 之后才判定，且与 Range 优先级不符 RFC 7232
`handlers/objects.cc:172-179`：先 `get_object(...range)` 再 `check_read_preconditions`。cloudproxy 后端上意味着已向上游拉取整对象再丢弃（可廉价放大）；且 `resolve_range` 的 416 在前置条件之前抛出，本该 412 的返回 416；`If-Range` 未实现。**建议**：先 head 判前置条件再建流，前置条件判定挪到 range 解析之前。

### [中 · confirmed] PUT 条件请求 head+put 非原子
`handlers/objects.cc:81-100`：`If-None-Match:*`/`If-Match` 各一次 head 再 put，中间无后端 CAS，两个并发写者都能通过检查后互相覆盖——"防覆盖"与"乐观并发"两个语义都不成立。**建议**：条件写下推到后端接口（`put_object` 加 `expected_etag`/`if_absent`，localfs rename 前查、duostore meta CAS），无法支持者明确 NotImplemented。

### [中 · confirmed] 对象键含 XML 非法控制字符 → 整个 ListObjects 响应不可解析；encoding-type 未实现
`xml.cc:194-208` `xml_escape` 只处理 5 实体；`validate.cc:23-47` 允许 0x01–0x1F。`PUT /b/a%01b` 成功 → `GET /b?list-type=2` 响应含裸 0x01 → 对任何合规 XML 解析器是 well-formedness error → 一个对象污染全桶不可列举。全代码库无 `encoding-type` 处理（既不实现也不拒绝）。**建议**：`validate_object_key` 拒绝控制字符或 `xml_escape` 输出数值实体；实现 `encoding-type=url`。

### [中 · confirmed] DeleteObjects 只捕 S3Error，非 S3 异常中断整批且丢失部分结果
`handlers/objects.cc:229-235`：只 `catch(const S3Error&)`。后端抛 `std::runtime_error`（getentropy/rocksdb/redis 传输异常）时逃到兜底返回 500，此前已删的 key 不出现在响应里，客户端无法知道删了哪些。**建议**：`catch(const std::exception&)` 映射为 InternalError 条目继续。

### [中 · confirmed] admin API 只捕 S3Error，其他异常回 XML 而非 JSON
`handlers/admin_credentials.cc:145-151`：`generate()` 的 getentropy/put 失败是 `runtime_error`，逃出后回 S3 XML，违反文件头"错误在本 handler 内渲染 JSON"承诺，管理面客户端解析失败。**建议**：追加 `catch(const std::exception&)` → 500 JSON。

### [中 · confirmed] 后端内部错误文本经 error_xml 原样外泄（含上游 endpoint）
`errors.cc:57-66` 把 `e.message` 写进响应；L3 的 `S3Error(InternalError, "…https://内部endpoint…")`（cloudproxy `remote_client.cc:370`）直接进响应体。dispatch 只收敛非 S3Error 的异常。**建议**：对 InternalError/SlowDown 统一替换固定文案，原文只进日志（request_id 已可关联）。

### [中 · plausible] remove() 与 sync_now() 竞态，已吊销凭证可复活一个同步周期
`credential_store.cc` `remove()`（读锁查→释放→`co_await delete_object`→写锁 erase）与 `sync_now()` 反方向无保护：sync 在 delete 生效前完成 list（对象仍在）、在 erase 后执行新增分支 → 把刚吊销的 AK 重新 emplace。"吊销即刻生效"被破坏。**建议**：remove 记 tombstone，sync 新增分支跳过近期 tombstone。

### [中 · plausible] 流式校验失败时数据已全部下发给后端
`sigv4.cc:142-145`（EOF 才抛 mismatch）。localfs/duostore 有 staging RAII 丢弃安全，但 cloudproxy 边读边往上游 PUT，异常时远端对象可能已完整写入（且由上面 high 条可知那里根本不抛）。**建议**：与 cloudproxy payload 校验条一并修，storage-backend 契约写明"读取中抛异常 ⇒ 后端不得提交"。

### [低→中 · confirmed] `/-/readyz` 无认证、放大后端调用、回显内部拓扑
`service.cc:90-101`（三个 `/-/` 端点在 verify 之前分流）、`:259-276`（`report += name + " FAIL: " + e.what()`）。匿名循环打 `/-/readyz` → 每次对 cloudproxy 发真实远端 ListBuckets（计费+限流）、对 localfs 扫 root 目录，并把含上游 endpoint 的异常文本回给调用方。**建议**：`/-/` 走独立访问控制（绑 admin 监听或要求 root）；readyz 只回 ok/fail + 后端名，细节进日志。

**核对无恙**：`.sys` 的 path-style / copy-source / ListBuckets 过滤三处拦截正确（唯一缺口是 vhost，见 README §1.1）；恒定时间签名比较；XML 解析不展开外部实体；write-through 崩溃一致性顺序。
