# s3（L2）评审明细

> 覆盖 `src/s3/`：service / router / auth（sigv4 / credential_store）/ handlers
> （objects / multipart / buckets / list_objects / admin_credentials / common.h）/
> xml / errors。跨模块问题（认证 fail-open、`percent_decode` 的 `+`）见
> [README.md](README.md) §1.2 / §1.3。

**模块级评价**：结构清晰、边界意识强（`.sys` 多处拦截、copy-source 单独授权、
write-through 顺序、恒定时间比较、XML 不展开实体都做对了）。系统性问题有三类：
**验签的"完整性校验"依赖下游读到 EOF、而 cloudproxy 后端不会**（payload 校验对该后端
形同虚设）；**若干客户端可控输入未设上限/未严格校验**（max-keys、amz-date 年份、空
摘要）；以及**条件写/条件读非原子且判定时机偏晚**。

> **2026-08-02 更新**：本文件所列问题已全部修复，各条目标注 ✅已修复。核心收敛：
> payload 校验不再绑 EOF（读满自报长度即比对，"body 须读到 EOF / 抛异常不得提交"
> 写进 `storage/backend.h` 契约并修正 cloudproxy 消费循环）；认证开关改为只升不降
> 并对凭证表清空加防护（README §1.2，本轮一并修复）；条件请求判定挪到建流之前并
> 实现 If-Range；max-keys 钳制 1000、对象键拒绝控制字符、实现 encoding-type=url。
> 单测新增 17 组用例；主构建 250 / TSan 235 测试全通过、无竞争告警。
> 跨模块问题中 README §1.3（`percent_decode`）不在本轮范围。

## 高

### [高 · ✅已修复] x-amz-content-sha256 校验与 aws-chunked 末块签名在 cloudproxy 后端从不执行
`src/s3/auth/sigv4.cc:135-147`（`Sha256VerifyingReader::read` 只在 `n==0` 分支比对）、`:194-223`（`ChunkedSigV4BodyReader` 的 chunk 签名/长度对账只在下一次 read 的归零处触发）；消费者 `src/storage/cloudproxy/cloudproxy_backend.cc:557` `while (sent < len)`（`len = body.length()`）。

**机制**：两个校验装饰器都把判定挂在 EOF 那一次 `read()` 返回 0 上。cloudproxy 生产者读满自报长度即退出，**永不再调 read()** → hex 摘要完全不验；signed chunked 模式下末块与 0 号尾块签名都不验，签名链在倒数第二块断掉，长度对账也不执行。其它 5 个后端是 `for(;;){n=read(); if(!n)break;}` 读到 EOF——契约没写下来，只是碰巧成立。**触发**：路由到 cloudproxy 的桶 `PUT` 带任意错误 `x-amz-content-sha256` → 200 且不报错。对能改写在途请求的中间人是签名保护的实际缺口。
**✅已修复**：校验不绑 EOF——`Sha256VerifyingReader` 读满 `length()` 即比对（失败时最后一块不交付下游）；`ChunkedSigV4BodyReader` 交付满 decoded length 后同步走完末块验签、0 号尾块与 trailer（`drain_to_done`），且 `x-amz-decoded-content-length` 改为必填（AWS 本就强制）；`cloudproxy_backend.cc` 生产循环改为读到 `read()==0` 为止；"body 须读到 EOF / 读取中抛异常 ⇒ 后端不得提交对象"写进 `storage/backend.h` 的接口契约。单测：只读满 length() 不读 EOF 的消费模式下 hex mismatch 与末块坏签名均检出。

### [高 · ✅已修复] ListObjects 的 max-keys 无上限，单请求即可把整桶列表构造进内存
`src/s3/handlers/list_objects.cc:12-18`（`stoi` 后只拒 `<0`）、`:24` 起 XmlWriter 全量拼进 `resp.small_body`。无 S3 的 1000 钳制。对百万级对象的桶发 `?list-type=2&max-keys=2147483647` → 数百 MB~GB XML → 单进程 OOM 打掉所有租户；localfs 还同步遍历整棵目录树。
**✅已修复**：`max_keys = min(max_keys, 1000)`（S3 语义静默钳制）；单测覆盖 `max-keys=2147483647` → `<MaxKeys>1000</MaxKeys>`。

### [高 · ✅已修复] 认证 fail-open（凭证表运行期变空）
详见 [README.md](README.md) §1.2。`sigv4.cc:389` + `credential_store.cc` 的 `apply_file_credentials`/`sync_now` 可把 `creds_` 清空导致匿名开放。
**✅已修复**（三层防护）：`SigV4Authenticator::enabled()` 改为**只升不降**的闩锁——一旦观察到凭证表非空即固化"必须认证"，此后表变空走 InvalidAccessKeyId（fail-closed）而非放行匿名；`apply_file_credentials` 拒绝把非空表清成空表（文件被误编辑成 `{"credentials":[]}` 时保留旧表 + LOG_ERROR）；`sync_now` 同理拒绝把最后一条凭证清掉（.sys 被外部清空场景）。两处触发后置 `degraded()`，`/-/readyz` 报 503 引导运维介入。单测：纯文件形态清空文件后旧凭证仍可用且 degraded。

## 中

### [中 · ✅已修复] parse_amz_date 对四位年份不设限 → chrono 有符号溢出 UB，并绕过"未来时间戳"防护
`sigv4.cc:418` → `core/util/time.cc:73-83`。`sscanf("%4d…")` 接受 9999 年，`timegm`≈2.53e11 秒，`from_time_t` ×1e9 → 2.5e20 超 int64 → 溢出 UB。发生在凭证查表/签名比对**之前**，未认证可达。回绕还使 `sigv4.cc:423`（presigned 未来 15min 防护）与 `:437`（时钟偏移）形同虚设。
**✅已修复**：年份钳制 1970–2200 已随 core 评审修复落地（三个 parse 统一，见 [core.md](core.md)）；本轮补 `parse_amz_date` 的完整消费校验（`%n` 强制 'Z' 在场 + 总长 16，拒尾部垃圾）。

### [中 · ✅已修复] `?versionId` 未拒绝，`DELETE ?versionId=` 静默删当前对象
`service.cc:39-46` `kUnsupportedSubresources` 含 `"versions"` 但不含 `"versionId"`；路由兜底吃下它。`handlers/common.h:66` 对 copy-source 的 versionId 是拒绝的，直接对象路径漏了。
**✅已修复**：`"versionId"` 加入拒绝表 → 501 NotImplemented；单测验证对象不被误删。

### [中 · ✅已修复] 声明空 payload 摘要时跳过 body 校验，body 脱离签名保护
`sigv4.cc:496`：为给真·空 body 省一次哈希，把 `x-amz-content-sha256: e3b0c442…` 排除校验，但不检查 body 是否真空 → 空摘要 + 非空 body 被原样落盘。
**✅已修复**：空摘要照样包 `Sha256VerifyingReader`（空 body 只多付一次空哈希）；单测：空摘要 + 非空 body → XAmzContentSHA256Mismatch。

### [中 · ✅已修复] 不强制 host ∈ SignedHeaders，vhost 下 presigned 可跨桶重指向
`sigv4.cc:388-500`。AWS 规定 host 必签，此处只小写化 signed_headers 不检查是否含 host（presigned 甚至允许 SignedHeaders 缺失）。vhost 下 bucket 来自 Host 头；签名未绑 host 时，同一 presigned 签名在任意 `*.base_domain` 上都成立 → 改 Host 即跨桶。
**✅已修复**：`verify()` 强制 signed_headers 含 `host`（header 认证与 presigned 一致），缺失 → AuthorizationHeaderMalformed。

### [中 · ✅已修复] 条件请求在 get_object 之后才判定，且与 Range 优先级不符 RFC 7232
`handlers/objects.cc:172-179`：先 `get_object(...range)` 再 `check_read_preconditions`。cloudproxy 后端上意味着已向上游拉取整对象再丢弃（可廉价放大）；且 `resolve_range` 的 416 在前置条件之前抛出，本该 412 的返回 416；`If-Range` 未实现。
**✅已修复**：条件头（或 If-Range）存在时先 `head_object` 判定 412/304，再按需建流——前置条件先于 range 的 416（RFC 7232 优先级）；实现 `If-Range`（强 ETag / HTTP-date 精确匹配，验证器不中则忽略 Range 回整对象）；无条件头的 GET 不多付 head。单测三组（412 压过 416 / If-Range 命中与不中）。

### [中 · ✅已修复] PUT 条件请求 head+put 非原子
`handlers/objects.cc:81-100`：`If-None-Match:*`/`If-Match` 各一次 head 再 put，中间无后端 CAS，两个并发写者都能通过检查后互相覆盖。
**✅已修复**：条件 PUT 的 head 检查 + put 在 per-key 条带异步锁（`S3Service::cond_put_lock`，64 条带 `AsyncSemaphore(1)`）内串行化，本进程内两个并发条件写不再都能通过检查。多实例共享后端时仍需后端级 CAS——当前部署形态为单网关写入，该限制注释在 `service.h`；后端接口下推（`expected_etag`）留待后续。

### [中 · ✅已修复] 对象键含 XML 非法控制字符 → 整个 ListObjects 响应不可解析；encoding-type 未实现
`xml.cc:194-208` `xml_escape` 只处理 5 实体；`validate.cc:23-47` 允许 0x01–0x1F。`PUT /b/a%01b` 成功 → `GET /b?list-type=2` 响应含裸 0x01 → 对任何合规 XML 解析器是 well-formedness error → 一个对象污染全桶不可列举。全代码库无 `encoding-type` 处理。
**✅已修复**：`validate_object_key` 拒绝控制字符（0x00–0x1F、0x7F；XML 1.0 连数值实体都无法表示它们，转义救不了）；实现 `encoding-type=url`（Key/Prefix/Delimiter/Marker/NextMarker/CommonPrefixes 经 URL 编码，响应带 `<EncodingType>url</EncodingType>`；其他取值 → InvalidArgument）。

### [中 · ✅已修复] DeleteObjects 只捕 S3Error，非 S3 异常中断整批且丢失部分结果
`handlers/objects.cc:229-235`：只 `catch(const S3Error&)`。后端抛 `std::runtime_error`（getentropy/rocksdb/redis 传输异常）时逃到兜底返回 500，此前已删的 key 不出现在响应里。
**✅已修复**：追加 `catch(const std::exception&)` → 该 key 记 InternalError 条目继续整批；原始文案只进日志。

### [中 · ✅已修复] admin API 只捕 S3Error，其他异常回 XML 而非 JSON
`handlers/admin_credentials.cc:145-151`：`generate()` 的 getentropy/put 失败是 `runtime_error`，逃出后回 S3 XML，违反文件头"错误在本 handler 内渲染 JSON"承诺。
**✅已修复**：追加 `catch(const std::exception&)` → 500 JSON 固定文案；S3Error 分支的 InternalError 文案同样收敛（原文进日志）。

### [中 · ✅已修复] 后端内部错误文本经 error_xml 原样外泄（含上游 endpoint）
`errors.cc:57-66` 把 `e.message` 写进响应；L3 的 `S3Error(InternalError, "…https://内部endpoint…")`（cloudproxy `remote_client.cc:370`）直接进响应体。
**✅已修复**：dispatch 的 S3Error 路径经 `public_error` 收敛——InternalError/SlowDown 统一固定文案，原文带 request_id 进日志；admin JSON 路径同步处理。

### [中 · ✅已修复] remove() 与 sync_now() 竞态，已吊销凭证可复活一个同步周期
`credential_store.cc` `remove()`（读锁查→释放→`co_await delete_object`→写锁 erase）与 `sync_now()` 反方向无保护：sync 在 delete 生效前完成 list（对象仍在）、在 erase 后执行新增分支 → 把刚吊销的 AK 重新 emplace。
**✅已修复**：`remove()` 在 delete 之前记 tombstone（delete 失败则回收）；`sync_now` 新增分支跳过 TTL（max(60s, 2×sync_interval)）内的 tombstone，过期自动清理。单测：remove 后把对象放回存储再 sync，不复活。

### [中 · ✅已修复] 流式校验失败时数据已全部下发给后端
`sigv4.cc:142-145`（EOF 才抛 mismatch）。localfs/duostore 有 staging RAII 丢弃安全，但 cloudproxy 边读边往上游 PUT，异常时远端对象可能已完整写入。
**✅已修复**（与上面 cloudproxy 高危条同一次收敛）：mismatch 在最后一块交付下游**之前**抛出；cloudproxy 读侧异常触发 `abort()` 中止在途远端传输（Content-Length 不满的上传远端不落对象）；契约写入 `storage/backend.h`。

### [低→中 · ✅已修复] `/-/readyz` 无认证、放大后端调用、回显内部拓扑
`service.cc:90-101`（三个 `/-/` 端点在 verify 之前分流）、`:259-276`（`report += name + " FAIL: " + e.what()`）。匿名循环打 `/-/readyz` → 每次对 cloudproxy 发真实远端 ListBuckets（计费+限流）、对 localfs 扫 root 目录，并把含上游 endpoint 的异常文本回给调用方。
**✅已修复**：异常文本只进日志，响应只回 `<backend> ok/FAIL`；结果 5s 短缓存 + 单飞（并发探测只放一个，其余回上次结果）——匿名循环打不出对后端的放大调用。探活语义保持无认证（LB/k8s probe 无法签 SigV4）；另将凭证清空防护的 `degraded` 状态纳入 readyz（503）。独立 admin 监听留作后续加固。

**核对无恙**：`.sys` 的 path-style / copy-source / ListBuckets 过滤三处拦截正确（唯一缺口是 vhost，见 README §1.1）；恒定时间签名比较；XML 解析不展开外部实体；write-through 崩溃一致性顺序。
